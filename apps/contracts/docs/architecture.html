A strategy that holds stocks for you, and cannot be made to do what you did not allow

This is the onchain side of Sandworm Stocks, in one page: what each contract is, why it is a separate piece, and where each rule is kept. Everything below is built and tested on simulated stocks (mock tokens, pools and a router). Nothing has run against real Base contracts, and nothing here has been audited.

The big idea

A vault is deployed with a set of rules. Each rule is placed on its own: some are kept by the chain, some by the app, some by both. The app is clever and can be wrong; the chain is strict and cannot be talked into anything.

The pattern is Zyfai's: the agent proposes and an onchain gateway decides. A compromised app can lose, at most, what the chain's limits let one trade lose.

The layers

Each layer is a separate set of contracts, so any one can be audited alone and replaced without the others changing.

Triggers (Reactive contracts that start an exit from a pool event) sit beside these. The stop-loss pair exists for classic Aerodrome pools; the vault's own triggers are designed, not built.

The account: a host with typed plugin slots

The vault is an ERC-7579 account. Modules are installed and removed by the owner, and each has a type. That is the plugin system: nothing else needs to change when one is added.

The keeper does not call the account. It asks the executor module, and the module asks the account, so the keeper key can do one thing only.
Honest limits of the reference account. It is for simulated stocks and testnets and is not audited. It has no ERC-4337 yet (the owner calls it directly), no validators, one hook slot. Production should use an audited ERC-7579 account (Safe with Safe7579, as Zyfai does, or Nexus). Every module here is written to the standard's interfaces, so it moves with no change.

Rules: every rule is a module, deployed with the vault, each placed on its own

A rule is an id, a placement and a value. The placement is chosen per rule, and that includes the limits. A rule is on-chain exactly when its module is attached to the vault: there is no list of rules inside the guard. Add a kind of rule by writing one small contract; the core never changes.

on-chain a guarantee

Its module is attached to the vault. It refuses what breaks it, whoever asks, the app included.

off-chain a promise

The app keeps it. It is written into the vault's record (with the hash of its function, if it has one) so it can be checked, but nothing onchain stops a breach.

both belt and braces

The module is attached and the app keeps it too. The app can stop short of the chain's limit; the chain catches the app if it ever does not.

How a rule gets onto a vault

Rules that chain

A composite rule is itself a module that holds other modules, so rules combine to any depth. Each module keeps its value per caller, so a composite attaching a child cannot change what the guard gave it.

Why modules and not a list in the guard: a list inside the guard means every new kind of rule changes the part that holds the money, and the guard has to name what it enforces (which is what a hard-coded list of ids was, and it was removed). Now a vault enforces what its attached modules enforce, and nothing else claims it.

Off-chain rules: a function, a hash, and a number the chain reads back

Some rules need data no chain has: a sector, an earnings date, a market's hours, a correlation. They are still enforceable. Each is one function with its full text. The hash of the text is committed to on-chain. The app runs the function and posts the result; the module reads it and refuses a trade that breaks the vault's limit. It reads both ways: the app reads the rules from the chain, and the chain reads the app's results back.

Change one word, change everything

The hash, the rule's kind and the channel it reads all come from the text. A vault that names a hash cannot be attached to a module with a different one: it refuses.

One number, many vaults

A result about the market or one stock is posted once and judged by every vault that has the rule. A result about a vault, or its stock, is posted for that vault.

Chains with the rest

An off-chain rule is a module like any other, so it sits inside AND, OR, NOT and WHEN. "Buy only while the market is open and the VIX is under 30" is two of them in an AllOfRule.

Strategy blocks: one contract for each kind

A strategy is a tree of contract addresses. Every block answers one question: given the numbers now, what should be held? A block only reads, so it can do no harm whatever it contains.

Leaves

AssetBlock holds one stock whole. CashBlock holds nothing.

Groups

EqualGroup, SpecifiedGroup (shares given), InverseVolatilityGroup (the steadier child gets more). A stock in two children has its shares added.

Logic

IfBlock (one branch or the other), FilterBlock (top or bottom N by an indicator), RebalanceBlock (adds a policy: how often, and how far a stock may drift).

Conditions

ComparisonCondition (a reading against another or a number), AllCondition, AnyCondition.

Why a contract each: a block is a plugin. It is audited alone, reused by any strategy that points at it, and added later without touching the vault. A tree of addresses can be read, forked and checked by anyone: the same readings give the same answer for everyone. Turned down: one interpreter contract reading an encoded tree (one big thing to audit, changed by every new block type), and working it out in the app (then nothing onchain says why).

The owner is never limited. A call that came from the owner passes, so the owner can always take their money out. And if a module goes wrong, emergencyWithdraw and forceUninstall work without calling it. Only the owner can use either.

A hundred flows, run for real

Five strategies × five placements of the rules × four markets, each deployed and run on simulated stocks, each logged. All 100 pass. Run forge test --match-contract FlowTraces -vv to read them, and -vvvv on test_traceOneFlow for every call.

5 strategies

equal NVDA+AAPL · top-1 by return · top-2 weighted by steadiness · NVDA if RSI>70 else cash · 60/40 in a weekly-drift rebalance

5 rule placements

all on-chain · all off-chain · mixed limits · tight, on both · a custom kind from another module + an off-chain stop

4 markets

flat · NVDA doubles · NVDA halves · a price spike out of line with its average

Every one of the 100 flows passed these checks:

  1. The executor never builds a trade the guard refuses.
  2. After any rebalance, no router holds a permission to take anything.
  3. A limit placed on-chain, or on both, holds: no stock is over its share.
  4. Only fees are lost: after a rebalance the vault is worth at least 98% of what it was just before.
  5. The owner can always take everything out.
  6. A pool whose price is out of line with its average is not traded in.

Decisions, and why

Each says what was chosen, what was turned down, and what it costs.

The app proposes; the chain disposes

Why: a compromised or mistaken app must not be able to lose the person's funds. Turned down: an executor with free rein, because the safety would rest on our server's keys.

An ERC-7579 account

Why: typed modules installed and removed by the owner is exactly the plugin system, and it is a standard other tools understand (Zyfai builds on it). Cost: the reference account here is not audited and has no ERC-4337; production should use an audited one.

The guard checks calls, not intentions

Why: an executor's calls are decoded and checked for address, function and values, the way Zyfai's gateway does. A bug this found: the guard first checked "approve no more than is held" before the batch ran, but a rebalance sells first and its buys are funded by the sale. It refused honest rotations. Now it checks afterwards that no permission is left open, which is stronger and has no ordering problem.

Numbers come from a board

Why: the chain cannot see Yahoo or 126 days of history for every stock. The board is the narrowest door for off-chain data: it refuses stale, out-of-order, future-dated or wild numbers. Cost: the publisher can be wrong, which is why the rules still apply whatever it posts.

A registry of what may be traded

Why: the token, the pool and the router are what an attacker would swap. They are pinned, and checked on every trade. Turned down: letting a strategy name any token.

The owner's way out is outside the modules

Why: ERC-7579's own review warns that a module can lock an account. emergencyWithdraw and forceUninstall do not call any module.

Simulated stocks first

Why: a test can put a stock at $100, then $50, make a pool shallow, or push a price out of line with its average on cue. No real market does. Cost: none of it has met the real Base contracts.
